# v0.3 Pilot Web App

## Goal

v0.3 turns AI VOC Ops from a local demo into a pilot-ready Streamlit application that external testers can use safely enough for structured model feedback.

The pilot is not a production customer-support system.

## Pilot loop

1. Tester enters one synthetic or de-identified VOC.
2. Common email, phone-number, and long-number patterns are masked before the OpenAI API call.
3. The model returns category, subcategory, priority, sentiment, human-review flag, and reason.
4. The tester marks the result correct or supplies corrected labels.
5. Feedback is stored in the current Streamlit session.
6. If Supabase is configured, the same redacted feedback is persisted.
7. An operator exports persisted feedback into a `provisional` review queue.
8. Only after manual review may rows be promoted to `label_status=reviewed` and used for publishable v0.2 evaluation metrics.

## Safety limits

Default values:

- single-text length: 4,000 characters
- single-VOC analyses per Streamlit session: 20
- CSV batch size: 100 rows

Environment variables:

```text
PILOT_MAX_BATCH_ROWS=100
PILOT_MAX_TEXT_CHARS=4000
PILOT_MAX_SINGLE_ANALYSES_PER_SESSION=20
```

These are pilot safeguards, not strong internet-wide rate limiting. A new browser session can reset the per-session counter.

For the first pilot, use a restricted tester group and an OpenAI project with an explicit budget/spend limit.

## Local run

```bash
python -m pip install -r requirements.txt
streamlit run app/main.py
```

Open **Pilot Test** in the sidebar.

Without Supabase, feedback is session-only and the tester can download the current session as CSV.

## Persistent feedback with Supabase

Run `docs/supabase_pilot_feedback.sql` in a Supabase project.

Configure:

```text
SUPABASE_URL=...
SUPABASE_ANON_KEY=...
SUPABASE_FEEDBACK_TABLE=pilot_feedback
```

The public app only needs the anon key. The SQL policy grants anonymous INSERT but does not grant anonymous SELECT.

Do **not** put a Supabase service-role key in a public Streamlit deployment.

## Streamlit Community Cloud

Deploy `app/main.py` from the repository branch you want to test.

Put root-level secrets in Streamlit's Secrets settings, for example:

```toml
OPENAI_API_KEY = "..."
OPENAI_MODEL = "gpt-5.6-luna"
OPENAI_REASONING_EFFORT = "none"

PILOT_MAX_BATCH_ROWS = "100"
PILOT_MAX_TEXT_CHARS = "4000"
PILOT_MAX_SINGLE_ANALYSES_PER_SESSION = "20"

SUPABASE_URL = "..."
SUPABASE_ANON_KEY = "..."
SUPABASE_FEEDBACK_TABLE = "pilot_feedback"
```

Keep secrets outside Git.

## Export feedback for review

Only on a trusted local/admin machine:

```text
SUPABASE_SERVICE_ROLE_KEY=...
```

Then run:

```bash
python -m evals.export_pilot_feedback
```

Output:

```text
evals/results/pilot_feedback_review_queue.csv
```

Every exported row is intentionally:

```text
source_type=pilot_feedback
label_status=provisional
label_version=v0.3-pilot
```

Review the labels manually before using them in the gold dataset.

## Suggested first pilot protocol

Ask each tester for 5-10 de-identified cases covering a mix of:

- simple informational VOC
- refund/payment risk
- delivery boundary cases
- product defect/damage cases
- complaint/privacy risk

A useful first pilot is not defined by a target accuracy chosen in advance. The goal is to collect enough reviewed feedback to identify repeated failure modes and then evaluate the same cases consistently.

## Known limitations

- PII masking is pattern based and cannot guarantee removal of names, free-form addresses, or every identifier.
- Session limits are not production-grade abuse prevention.
- The public pilot should never accept confidential former-employer data.
- Tester feedback is not automatically treated as ground truth.
- Persistent feedback requires a separately configured Supabase project.
