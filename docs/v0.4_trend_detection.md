# v0.4 Trend Detection Core

## Purpose

The v0.4 core answers four operational questions from already structured VOC
rows: what changed, how much it changed, when it changed, and which records
support the finding. It is a deterministic backend foundation for a later
Streamlit Trend UI. It does not call OpenAI, write to Supabase, or generate
natural-language explanations.

## API and input contract

```python
from app.services.trend_detector import analyze_trends

result = analyze_trends(
    results,
    timestamp_column="created_at",
    frequency="weekly",
    dimension="subcategory",
)
```

The input must contain the configured timestamp column and `category`. The
`subcategory` column is required when `dimension="subcategory"`. Existing
classifier output columns are consumed as-is; the service does not rewrite
`category`, `subcategory`, `customer_message`, or the timestamp.

`result.period_metrics` contains one row for every observed issue and every
calendar period between the first and last usable timestamp. It includes the
canonical category/subcategory values, an explicit `period_start` and
`period_id`, the count, and evidence references. `result.alerts` contains the
latest-period comparison for every issue, ranked with alerts first. It exposes
the comparison, baseline, guardrail, score components, alert class/reason, and
current-period evidence. `result.data_quality` contains lightweight counts and
history state.

## Frequencies and period boundaries

`daily` uses a UTC calendar day. `weekly` uses Monday through Sunday in UTC and
stores Monday as `period_start`; the period ID is the ISO date of that Monday.
The frequency is explicit and only `daily` and `weekly` are supported.

The latest available calendar period is compared with the immediately preceding
calendar period. Empty calendar periods are represented as zero-count rows so a
new or returning issue is not hidden by a missing group-by row.

## Comparison and zero-baseline behavior

For each issue:

```text
absolute_change = current_count - previous_count
percentage_change = absolute_change / previous_count * 100  (previous_count > 0)
```

When the previous count is zero, `percentage_change` is `None`. The comparison
state is `new_issue` when the current count is positive and `no_change` when
both counts are zero. With only one available period the state is
`no_previous_period`. Infinity is never emitted.

## Guardrails and spike score

The defaults are explicit operational guardrails:

```text
min_current_count = 5
min_absolute_increase = 3
baseline_periods = 4
```

They are configurable and are not statistically tuned thresholds. A row is an
alert only when the current count and absolute increase meet both guardrails
and a previous period exists. A positive change that fails a guardrail remains
visible as `normal` with a reason such as `below minimum-volume guardrail`.

An emerging issue (`alert_class="emerging"`) is a meaningful current volume
whose previous count is zero. Other guarded increases are `spike`. All other
rows are `normal`.

When at least four completed periods precede the current period, the service
calculates a population standard-deviation baseline. The transparent score is
the sum of:

```text
volume component
+ positive absolute-change component
+ positive relative-change component
+ positive baseline z-score component
```

The component columns are returned with every comparison, so an operator can
see why an issue ranked above another. A zero-variance baseline is reported as
`baseline_state="zero_variance"`, has no z-score, and still has a finite score
from the direct comparison components. If there are not enough periods, the
state is `insufficient_history` and `spike_score` is `None`; direct counts and
guardrail decisions remain available without manufacturing an anomaly score.

## Evidence traceability

Every period metric and alert carries `evidence_ticket_ids` for the supporting
rows in that period. When `ticket_id` is absent, `evidence_ticket_ids` is empty
and `evidence_row_indices` contains stable zero-based source positions. The
service does not concatenate full customer messages into result fields, so a
future detail view can retrieve the original rows by these references.

## Data quality

Timestamp parsing accepts pandas datetime values, ISO-like strings, and
timezone-aware values. Invalid nonblank timestamps and missing/blank timestamps
are excluded from aggregation and counted separately as
`invalid_timestamp_rows` and `missing_timestamp_rows`. A malformed row does not
abort the rest of the analysis.

Missing category and subcategory values are counted separately. Rows missing
the selected dimension are excluded from usable metrics. `input_rows`,
`usable_rows`, `periods_available`, `observed_periods`, frequency, dimension,
and baseline requirements are returned in `data_quality`.

## Controlled fixture validation

The focused test suite covers daily and weekly aggregation, category and
subcategory dimensions, period comparisons, zero baselines, minimum-volume
protection, clear spikes, stable series, tiny denominators, emerging issues,
multiple-issue ranking, insufficient history, zero variance, malformed and
missing timestamps, evidence references, missing dimensions, and input
immutability.

These fixtures prove deterministic service behavior only. They are not model
accuracy, precision, recall, F1, false-positive, or production performance
measurements.

## Known limitations

- Only daily and Monday-start weekly periods are supported; monthly periods are
  intentionally deferred.
- The latest available period is used as current; a production calendar or
  business-hours cutoff is not modeled.
- The score is an explainable operational ranking heuristic, not a statistical
  significance test or trained anomaly model.
- Source rows must already contain usable classification columns; the service
  does not classify or repair missing labels.
- Trend UI, issue details, Root Cause Analysis, QA, and weekly reporting are
  separate future milestones.
